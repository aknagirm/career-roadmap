# 4.1 Inputs to Large Language Models

[↑ Chapter Overview](<4. Prompt Optimization and Evaluation.md>) · [Model Parameter Details](<4.1.1 Model Parameters.md>) · [Next Topic: 4.2 Need for Prompt Evaluation →](<4.2 Need for Prompt Evaluation.md>)

Prompt quality should be judged by measurable output performance, not by how detailed or sophisticated the prompt sounds. Prompt optimization is therefore an evidence-based process: test the workflow, evaluate its outputs, and tune the controllable inputs.

## Three Controllable Inputs

An LLM's output is shaped by:

1. **Model** — Determines the system's underlying capabilities and limitations.
2. **Model parameters** — Settings such as temperature and token limits influence randomness, consistency, and response length.
3. **Prompt** — Provides instructions, context, examples, constraints, and the expected output format.

Changing any one of these inputs can change the result, so they should be evaluated together rather than in isolation.

## Core Evaluation Qualities

LLM outputs are commonly evaluated across four task-quality axes:

- **Relevance** — Whether the response addresses the user's actual need, not merely the surface topic. An answer can appear related while still missing the underlying intent.
- **Correctness** — Whether the response is factually accurate and grounded. Evaluation may use task-specific rubrics such as source-faithfulness checks and hallucination detection.
- **Variability** — How consistently the system performs across repeated runs with the same input. A prompt that succeeds 80% of the time behaves very differently in production from one that succeeds 95% of the time.
- **Coherence** — Whether the response follows consistent internal logic. This is especially important in long-form content, where contradictions can appear across multiple paragraphs.

These qualities can conflict. Lower variability improves predictability but may reduce creativity on open-ended tasks. Maximizing relevance can also increase factual drift if the model tries too hard to satisfy a request without reliable information.

The task determines the priority. Production classification usually requires high correctness and low variability, while ideation can allow greater variability. The model, parameters, and prompt should then be tuned around those priorities and trade offs.

## Model Choice

The selected model sets a hard ceiling on achievable output quality. Prompt engineering can guide existing capabilities, but it cannot create a capability the model fundamentally lacks. For example, rephrasing a prompt cannot make a model perform arithmetic reliably if the model itself is unable to do so.

Models differ in:

- Depth of reasoning on multi-step problems
- Factual recall
- Instruction-following precision
- Output-format consistency
- Context-window size
- Cost and latency

They also respond differently to instructions, few-shot examples, and negative instructions. A prompt optimized for one model may underperform on another, so switching models often requires prompt re-evaluation and optimization.

**Intelligence density** means useful performance per dollar. For certain tasks, a capable 10B or 35B model may provide better cost-adjusted results than a much larger frontier model.

Model choice is therefore an ongoing design variable. It should be revisited as the task, operational constraints, and available models change.

## Model Parameters

Model parameters shape how a model expresses its response rather than changing its underlying capabilities. Important parameters include:

- **Max tokens** — Controls output length and affects cost, latency, and truncation risk.
- **Temperature, Top-p, and Top-k** — Control randomness and diversity.
- **Frequency and presence penalties** — Help manage repetition and encourage novelty.
- **Stop sequences** — End generation at defined content boundaries.

Parameters interact rather than acting as independent switches. For example:

- High temperature encourages randomness, while low Top-p restricts the candidate pool. Using both can create conflicting behavior.
- Frequency and presence penalties reduce repetition but may damage structured outputs that require repeated tokens or concepts.
- Higher max tokens gives complex answers more room to finish but can increase cost, latency, and unnecessary verbosity.

Change one parameter at a time during evaluation. Changing several settings together makes it difficult to identify what caused an improvement or regression.

For reproducibility, version the prompt together with the model and complete parameter configuration, including temperature, Top-p, max tokens, penalties, and stop sequences. This allows results to be audited, compared, rolled back, and improved systematically.

## Components of Prompt Engineering

The prompt is the most frequently tuned input because it is usually the cheapest and easiest to change, not because it is always the most powerful lever.

An effective prompt can be analyzed through five components:

1. **Instruction** — Defines the task, persona, and explicit goal. System and user instructions tell the model what role to follow and what outcome to produce.
2. **Context** — Provides grounding data such as retrieved passages, conversation history, or source documents.
3. **Examples** — Supplies few-shot demonstrations of good outputs. A few relevant examples can be clearer than long abstract instructions.
4. **Constraints** — Defines the output schema, length limits, and negative instructions so the response follows the required format and avoids unwanted content.
5. **Reasoning guidance** — Uses techniques such as step-by-step decomposition, chain-of-thought scaffolding, or self-critique to guide intermediate reasoning and reduce plausible but incorrect answers.

When debugging a prompt, identify which component is failing:

- **Wrong format** usually points to weak or unclear constraints.
- **Wrong content** often indicates missing context or unclear instructions.
- **Plausible but incorrect answers** may indicate insufficient reasoning or verification guidance.

This structure supports targeted changes instead of repeatedly rewriting the entire prompt without knowing what failed.

## Safety and Bias

Safety and bias form another evaluation area, but they require separate ethical and cultural consideration:

- **Safety** checks whether the model avoids harmful responses and follows appropriate moral or behavioral boundaries.
- **Bias** examines whether outputs unfairly favor, disadvantage, or misrepresent particular groups or viewpoints.

A major concern is that a small number of model providers can define acceptable behavior for users across different cultures and contexts. Their embedded values may not align with every user or application.

Safety controls should therefore be evaluated transparently and with input from affected users and deploying organizations. Where possible, those groups should have meaningful control over value-alignment decisions rather than having every boundary dictated entirely by the model provider.
