# 4.8 Evaluating Models: Cost vs. Performance Trade-offs

[← 4.7 Prompt Stability and Output Evaluation](<4.7 Prompt Stability and Output Evaluation.md>) · [↑ Chapter Overview](<4. Prompt Optimization and Evaluation.md>)

Model selection is a dynamic optimization problem rather than a one-time configuration decision. Teams must balance quality, cost, latency, consistency, and operational constraints throughout the system's lifecycle.

## Ongoing Model Re-evaluation

Once a prompt and evaluation protocol are established, regularly ask: **Is this still the right model for the task?**

Re-evaluation is necessary because providers release new models and change capabilities, pricing, rate limits, and latency characteristics. Keeping a model fixed indefinitely can leave a system paying more than necessary or delivering less quality than newer alternatives.

Use the same versioned evaluation protocol to determine whether another model offers:

- Better quality at a similar cost
- Similar quality at a lower cost
- Comparable quality with lower latency
- Better consistency or format reliability
- Stronger compliance with current technical and budget requirements

A consistent protocol separates measurable improvement from provider claims or novelty. Revisit the decision on a defined schedule and when pricing, models, traffic, requirements, or production failure patterns change.

## Why Model Choice Is Complex

Changing a model affects the entire workflow, not only the API configuration.

### Task-Specific Quality

Models perform differently across workloads. Broad benchmarks help with initial screening but may not predict performance on specialized tasks, domains, data, or failure cases. Candidate models must be tested on the application's own evaluation set.

### Latency and Throughput

Models differ in time to first token, total response time, and request throughput. Larger or reasoning-intensive models may be too slow for interactive workflows even when they produce higher-quality answers.

### Cost at Scale

Input and output token prices can vary by 20× or more across models and usage tiers. Small per-request differences can become large budget changes after accounting for traffic, long contexts, retries, and repeated evaluation calls.

### Output and Integration Reliability

Support and reliability for JSON mode, structured output, tool use, function calling, and schemas vary across models. Format inconsistency can break parsers and downstream systems even when the natural-language content is good.

### Stability

Models can show different levels of variation across repeated runs. Measure answer agreement, format reliability, and failure frequency rather than assuming that similar average quality means similar production predictability.

### Prompt Portability

A prompt tuned for model A may underperform when used unchanged with model B because models interpret instructions, constraints, examples, and formatting differently.

#### Instruction Following

Some models follow negative instructions such as *“do not mention X”* or *“avoid Y”* more reliably than others. Test these constraints after every model change. Where practical, state the desired positive behavior as well as the prohibition. Prompt-level restrictions should not be the only control for critical safety requirements.

#### Few-Shot Sensitivity

Models may need different numbers or types of examples. One model might perform well with three demonstrations, while another may need approximately ten to achieve comparable results. These numbers are illustrative and must be measured for the specific task.

Additional examples increase input tokens, cost, and latency. Evaluate whether each example contributes enough quality to justify its operational impact.

### Token and Context Handling

Context-window size, tokenization, usable long-context performance, and output budgets differ across models. A smaller or less effective context window may require:

- Fewer few-shot examples
- More selective retrieval
- More aggressive source summarization
- Different chunking or prompt composition
- Smaller output limits

Advertised context capacity does not guarantee that every part of a long prompt will be used equally well. Test information placement and retrieval quality on representative long inputs.

### Re-optimization After a Model Change

When migrating models:

1. Recheck instruction and negative-constraint compliance.
2. Retune the number, order, and content of few-shot examples.
3. Rebalance retrieved context against token cost and latency.
4. Revalidate structured output and downstream parsing.
5. Compare quality and stability on the same evaluation set.

Treating prompts as automatically portable risks degraded quality, inconsistent behavior, and unexpected cost. Model migration requires measured prompt adaptation rather than a direct configuration swap.

## Model Migration Is a Project

Migrating models affects quality, latency, cost, output formats, stability, prompts, and downstream integrations. Treat the change as a planned project with explicit acceptance criteria, time, and budget.

### Migration Process

1. **Capture the current baseline** — Record the existing model, prompt, parameters, evaluation results, traffic cost, and latency.
2. **Test prompt transfer** — Run the new model with the existing prompt to identify compatibility differences.
3. **Re-optimize for the new model** — Adapt instructions, few-shot examples, parameters, context usage, and output schemas.
4. **Re-run the evaluation protocol** — Compare correctness, faithfulness, completeness, safety, stability, cost, and latency on representative and difficult cases.
5. **Validate integrations** — Test JSON parsing, tool calls, schemas, retries, error handling, and every downstream consumer.
6. **Roll out gradually** — Use controlled traffic, monitor regressions and costs, and maintain a tested rollback path.

The transferred prompt provides a useful compatibility baseline, but it may make the new model appear worse simply because it was tuned for the old one. Final selection should compare appropriately optimized configurations for both models.

Budget for prompt experiments, evaluation runs, regression analysis, load testing, integration changes, monitoring, and rollback preparation. This controlled process makes trade-offs visible and reduces the risk of degraded user experience or unexpected costs.

## Four Model-Selection Axes

Model comparison should cover quality, cost, latency, and consistency rather than relying only on a benchmark score or advertised token price.

### Quality

Measure correctness, faithfulness, completeness, relevance, and task-specific failure rates on representative data. Higher quality may justify greater cost when incorrect or unsupported outputs have serious consequences.

### Cost

Normalize input and output prices to a common unit, such as price per 1,000 tokens, and scale them to the expected workload:

```text
cost per request =
  (average input tokens / 1,000 × input-token price)
  + (average output tokens / 1,000 × output-token price)
```

Multiply this estimate by projected traffic. Include retries, self-consistency calls, evaluations, tool calls, caching behavior, and infrastructure costs. Longer contexts and additional few-shot examples increase runtime burden even when two models have similar advertised rates.

### Latency

Measure both:

- **Time to first token (TTFT)** — How quickly the user begins receiving a response.
- **Total generation time** — How long the complete output takes.

Compare percentile latency, such as p50 and p95, under realistic request sizes and concurrency. Interactive applications are especially sensitive to delayed first tokens and slow complete responses.

### Consistency

Run the same inputs repeatedly and measure answer agreement, quality variance, format reliability, and failure frequency. Lower unwanted variance generally supports more predictable production behavior, reproducible incidents, and easier debugging.

A complete model comparison reports all four axes separately so a strong result in one dimension does not hide unacceptable performance in another.

## Comparing Models Fairly

Use the same:

- Evaluation dataset and rubric
- Prompt objective, adapted only when necessary for each model
- Output constraints
- Traffic assumptions
- Number of repeated trials
- Measurement environment

Record the exact model version, prompt version, parameters, date, and pricing assumptions so the comparison can be reproduced.

## Radar Charts

A radar chart visualizes several model dimensions on separate axes, such as quality, cost efficiency, latency efficiency, and consistency. A point farther from the center represents stronger performance on that normalized axis.

To compare models fairly:

1. Use the same scale and measurement period for every model.
2. Convert each axis so that higher always means better. For example, represent raw cost and latency as cost efficiency and latency efficiency.
3. Mark minimum acceptable thresholds and identify the application's priority axes.
4. Plot results from the same evaluation dataset and workload assumptions.

A larger polygon may suggest broader performance, but total area should not determine the winner. Radar-chart area is sensitive to axis order and scaling, and strong performance on low-priority axes cannot compensate for failing a critical requirement.

Application needs determine the best fit:

- A **customer-service bot** may prioritize low latency and cost because users expect fast responses and traffic is high. Quality must still meet a defined minimum.
- A **legal-research tool** may prioritize correctness and faithfulness even when the selected model costs more or responds more slowly because errors carry greater risk.

Radar charts make trade-offs visible and help compare models against explicit priorities. They discourage choosing a model only because it is new, large, or popular, but should be used with thresholds, measured data, and other decision methods rather than as a standalone ranking.

## Pareto Optimality

**Pareto optimality** identifies models where the trade-offs are genuine rather than wasteful.

### Dominated Models

Model A dominates model B when A is at least as good on every relevant dimension and strictly better on at least one. For example, A may have equal or higher quality and consistency while having equal or lower cost and latency.

A dominated model is usually removed from consideration because another option offers the same or better outcomes without requiring an additional sacrifice.

### Pareto Frontier

The **Pareto frontier** is the set of non-dominated models. Moving between models on this frontier requires a real trade-off:

- Higher quality may require higher cost or latency.
- Lower cost may require reduced quality, consistency, or capability.
- Lower latency may require a smaller model or a simpler reasoning process.

The frontier narrows the candidates but does not choose the winner. Teams must decide whether a quality improvement justifies its added cost or latency and whether savings justify any reduction in performance.

### Applying Pareto Analysis

1. Define which dimensions should be maximized, such as quality and consistency.
2. Define which dimensions should be minimized, such as cost and latency.
3. Remove models that fail mandatory thresholds.
4. Identify and remove dominated options.
5. Select from the frontier using application priorities and risk tolerance.

Account for measurement uncertainty before declaring one model dominant. Small score differences may reflect sampling noise, and the frontier can change when prices, traffic, prompts, or workloads change.

Pareto reasoning prevents teams from paying more for no measurable benefit and keeps selection focused on requirements rather than model size, novelty, or marketing.

## Practical Selection Process

1. Define minimum quality, safety, and latency requirements.
2. Benchmark candidate models on representative and difficult cases.
3. Measure repeated-run consistency.
4. Estimate end-to-end cost at expected traffic.
5. Remove dominated options.
6. Select the model whose trade-offs best match the application.
7. Re-evaluate periodically as models, prices, and requirements change.

## Responsible Model Selection

Model choice affects more than raw capability. Its full cost includes:

- **Direct financial cost** — Input and output tokens, repeated calls, tools, and infrastructure.
- **Latency and user experience** — Slow responses can frustrate users or make interactive workflows impractical.
- **Engineering effort** — Evaluation, prompt design, integration, monitoring, and maintenance require time.
- **Migration overhead** — Switching models may require prompt re-optimization, regression testing, and downstream changes.
- **Operational reliability** — Inconsistent formats or behavior can create incidents and support costs.

Quality, cost, latency, consistency, prompt behavior, and migration overhead form one decision space. Selecting a model casually or from popularity can lead to overspending, underperformance, or both.

A responsible process defines application constraints, measures candidates consistently, removes dominated options, and selects from the Pareto frontier according to real priorities. This produces a more sustainable balance between performance and total operational cost.
