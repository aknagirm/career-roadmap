# 4.5 Gold Datasets and Human Evaluation

[← 4.4 Task-Specific Evaluation for GenAI Workflows](<4.4 Task-Specific Evaluation for GenAI Workflows.md>) · [↑ Chapter Overview](<4. Prompt Optimization and Evaluation.md>)

Gold standard datasets and human evaluation form the foundation of trustworthy automated metrics. Automated scores are only meaningful when they are calibrated and validated against reliable ground truth.

## Why Gold Standards Matter

A gold standard contains examples that humans carefully label or evaluate using an explicit rubric. These trusted references define what good performance means before evaluation is scaled through automated methods.

Gold standards allow teams to:

- Calibrate and validate automated metrics or judges
- Detect incorrect and misleading outputs
- Compare prompts, models, and system versions consistently
- Improve workflows against an explicit target

Without a reliable gold standard, teams may optimize against vague or incorrect targets and make misleading performance claims. Human judgment anchors evaluation so systems can be improved and deployed more responsibly.

## Minimum Viable Evaluation Protocol

A practical minimum evaluation process has four steps:

1. **Define the task** — State in one sentence what the output must do. This forces clarity and prevents later disagreement about the goal.
2. **Choose metrics** — Ask what success means for this task, then select approximately two to four metrics from relevant categories rather than relying on one narrow score.
3. **Build test sets** — Curate an initial set of roughly 50 to 200 gold examples covering different difficulty levels, realistic inputs, and edge cases.
4. **Evaluate and version** — Compute and report the scores, and record the prompt version, model configuration, dataset version, and evaluation run together so results can be reproduced.

This protocol is a minimum viable evaluation system. A simple rubric, a modest gold dataset, and a repeatable scoring pipeline provide more practical value than an elaborate evaluation design that is never implemented.

Start with a small process that works, then improve it as new requirements and failure modes appear.

### Keep Rubrics Practical

Evaluation fails when a rubric is too complicated to apply consistently. A framework may look rigorous on paper but provide no value if humans or automated systems cannot use it quickly and repeatedly.

A practical rubric should be:

- Clear enough for reviewers to interpret consistently
- Fast enough to apply across the evaluation set
- Simple enough to automate or scale where appropriate
- Specific enough to produce actionable results

A simple rubric, 50 representative gold examples, and a repeatable scoring pipeline are more useful than a sophisticated framework that remains unused. Start with operational simplicity, measure real results, and add complexity only when evidence shows it is needed.

## Qualities of a Good Evaluation Set

A strong evaluation set should satisfy six properties:

1. **Representativeness** — Examples should reflect the real input distribution, including messy, incomplete, and typo-ridden queries rather than only clean demonstrations.
2. **Edge cases and known failures** — Include ambiguous inputs, difficult cases, and scenarios where the system has failed before. Missing these cases allows important failures to remain hidden.
3. **Difficulty bands** — Label examples as easy, medium, or hard to show where performance degrades. One average score can hide poor results on the hardest cases.
4. **Task coverage** — Represent every important production task and subtask. If users submit five query types, the evaluation set should contain meaningful coverage of all five.
5. **Human-labeled truth** — Give each example a trusted label, reference answer, or judgment created by a human following a rubric. This is costly, but weak labels undermine both evaluation and system improvement. Improving label quality can produce larger gains than further algorithm or prompt tuning.
6. **Regular refreshes** — Update the set as inputs and systems evolve. Add newly observed query types, edge cases, and production failures so the gold standard remains relevant.

Together, these properties make the evaluation set useful for finding weaknesses rather than merely confirming performance on ideal inputs.

### Choosing the Evaluation Set Size

Start with approximately **50 to 200 examples** for an initial evaluation signal. Measure the score distribution and variance before investing in a much larger labeling effort.

If results vary widely or the analysis requires reliable scores for smaller segments, increase the dataset size, such as by doubling it for the next evaluation round. Repeat this process until the scores are stable enough for the intended decision.

Dataset size should therefore be treated as a tunable parameter guided by observed variance and analysis needs rather than as a large, fixed commitment made upfront.

## Five-Step Curation Process

1. **Sample from production** — Use production logs where privacy, consent, and access controls allow. Real inputs reflect actual user behavior and unusual edge cases better than synthetic data. Use synthetic generation as a fallback or supplement rather than the only source.
2. **Tag difficulty** — Label examples as easy, medium, or hard. This enables stratified analysis and helps teams focus on difficult, high-impact cases.
3. **Add adversarial content** — Deliberately include known failures, tricky inputs, and hard edge cases so evaluation probes weaknesses instead of only confirming strengths.
4. **Create reference outputs** — Have humans write expected answers or labels according to the rubric. This is often the most expensive step, but it provides the trusted ground truth needed for meaningful evaluation.
5. **Perform multi-review** — Give contested or ambiguous examples to multiple reviewers. Resolve disagreements and measure inter-annotator agreement to determine whether the rubric is clear or vague.

This process transforms raw examples into a structured gold dataset that can guide model and workflow improvement. It applies across specialized domains, including disability claims, defense reconnaissance, and postal-address resolution, where domain expertise is essential for correct labeling.

### Difficulty Bands and Prioritization

Tagging examples as easy, medium, or hard enables **stratified analysis**, where performance is measured separately for each difficulty level instead of being hidden inside one average score.

Easy cases may already perform reliably and need less immediate attention. Hard cases often create greater user dissatisfaction or operational risk, so improving them can produce a better return on annotation, engineering, and debugging effort.

Difficulty bands help teams prioritize resources while still monitoring every level for regressions. They turn evaluation data into a practical guide for deciding what to improve next.

### Adversarial Cases, References, and Multi-Review

Three practices make a gold dataset useful for diagnosing weaknesses:

- **Adversarial inclusion** — Add known failure modes, hard cases, and trick questions. These cases expose vulnerabilities instead of merely confirming success on easy inputs.
- **Reference outputs** — Ask humans to write expected answers using the rubric. Although expensive, these references establish what correct behavior looks like.
- **Multi-review** — Assign contested cases to multiple reviewers and measure inter-annotator agreement. Disagreements can reveal vague rubric instructions or genuinely ambiguous examples.

Together, these practices improve label quality, clarify evaluation standards, and turn evaluation into a diagnostic process rather than a superficial check.

### Example: Multi-Review in Drone Imagery

A large Department of Defense object-detection project used drone imagery for reconnaissance. Multiple image analysts reviewing the same images was recommended so the team could measure and improve classification agreement.

The program instead prioritized collecting a larger quantity of singly reviewed data. Reported accuracy remained below **40% after the first year** and below **50% after the second year**, forcing the effort to restart with multi-review and agreement checks.

The failed approach became a reported **$109 million lesson**: a large volume of inconsistently labeled data cannot replace smaller amounts of high-quality, consistently reviewed ground truth. Skipping inter-annotator agreement can make even heavily funded systems unreliable and expensive to rework.

### Example: Disability-Claims Records

A federal disability-claims project used AI to pre-read medical records and estimate claims. Buying enough records through commercial healthcare systems would have cost hundreds of dollars per record.

Instead, the project sampled a fraction of a percent of available records while preserving the distribution of disability cases encountered in practice. The resulting system reached **97% consistency**, exceeding the observed level of human agreement, at a small fraction of the expected data cost.

The example shows that alignment with the real input distribution can matter more than dataset size. Human agreement also provides a useful baseline for interpreting system consistency, although consistency alone does not prove factual correctness.

## Budgeting for Evaluation

Evaluation requires real engineering and subject-matter resources. A practical starting rule is to reserve about **20% of engineering effort and budget** for evaluation, then adjust the allocation according to risk, scale, and the cost of failure.

### The 20% Rule and ROI

The 20% allocation is a planning heuristic rather than a universal requirement. Spending too little on evaluation can place the remaining development investment at risk because teams may build and operate systems without knowing whether they improve quality or create new problems.

The same principle applies to software projects, marketing campaigns, and other business investments: measurement shows whether an initiative produces meaningful value. When ROI remains unclear, the initiative may have had limited impact, or the team may not have invested enough in a credible assessment plan.

Early evaluation supports faster course correction, prevents prolonged spending on ineffective approaches, and provides evidence about whether an initiative should be expanded, changed, or stopped.

### Human Evaluation Costs

- **Annotation time** — Each example may take from 30 seconds to 30 minutes, depending on complexity.
- **Reviewer training** — Annotators may need several hours to learn the rubric, with complex rubrics requiring more preparation.
- **Coordination and calibration** — Alignment meetings, disagreement resolution, and quality checks require additional time.
- **Relabeling** — Changes to the rubric or guidance may require existing examples to be reviewed again.

### Automated Evaluation Costs

- **Judge calls** — LLM-as-a-judge usage can multiply quickly when each rubric dimension requires a separate call. For example, 500 examples with three judge calls each produce **1,500 API calls per prompt iteration**.
- **Orchestration and reporting** — Evaluation pipelines need systems for running jobs, aggregating scores, and presenting results.
- **Human calibration** — Automated evaluators require ongoing checks against human judgments.
- **Storage and versioning** — Teams must preserve datasets, configurations, outputs, scores, and run histories.

Automation shifts evaluation costs rather than eliminating them. Budgeting these costs upfront helps teams design a realistic evaluation strategy instead of treating evaluation as an afterthought.

## Human Evaluation: Strengths and Limitations

Human reviewers can interpret ambiguity, apply context, and detect subtle errors that surface-level automated metrics may miss. This makes human evaluation especially valuable for complex, subjective, or high-stakes tasks.

However, human evaluation has important limitations:

- **Cost** — A review may take from 30 seconds to 30 minutes per example, depending on complexity.
- **Attention requirements** — Reliable labeling requires trained reviewers with sufficient focus and domain knowledge.
- **Speed** — Manual review is too slow for many large-scale or rapid iteration cycles.
- **Inter-annotator variance** — Different reviewers may score the same example differently.
- **Intra-annotator variance** — The same reviewer may make different judgments at different times.

These limitations reduce scalability and consistency. Human evaluation should establish and periodically check quality standards, but it is usually impractical as the only evaluation method.

## Automated Evaluation: Strengths and Limitations

Automated evaluation offers:

- **Speed** — Depending on the metric and infrastructure, systems can score thousands of examples per minute.
- **Lower marginal cost** — Repeated scoring is generally much cheaper than equivalent human review.
- **Consistency** — With fixed inputs and deterministic evaluators, the same example receives the same score without changes caused by reviewer fatigue or time of day.

Its limitations include:

- **Missed nuance** — Automated metrics may overlook context, subtle meaning, or domain-specific concerns.
- **Metric gaming** — Outputs can exploit surface-level patterns and receive high scores without genuinely improving.
- **Calibration requirements** — Automated scores must be validated against human-labeled examples before they can be trusted.
- **Evaluator variability** — Model-based judges may themselves be non-deterministic or biased unless carefully configured and monitored.

Over-reliance on automated signals without human calibration can reinforce shallow or misleading patterns, as illustrated by the earlier drone-imagery example. Automated evaluation should scale human-defined standards rather than replace them.

## Hybrid Human and Automated Evaluation

Human and automated evaluation are complementary rather than competing approaches. A practical hybrid workflow is:

1. **Humans define quality** — Create the rubric and label a small, carefully reviewed gold dataset.
2. **Calibrate automated judges** — Compare automated scores with the gold labels and adjust the evaluator until it approximates human judgment closely enough for the task.
3. **Scale with automation** — Evaluate thousands of examples for each prompt or system iteration to support rapid experimentation.
4. **Perform human spot checks** — Periodically review automated judgments and recalibrate when user expectations, data, or system behavior change.

Humans set and refine the standards; automated systems apply those standards with greater breadth and speed. This partnership combines human depth and nuance with machine scale and repeatability.

## Inter-Annotator Agreement

**Inter-annotator agreement (IAA)** measures how consistently trained reviewers label the same examples. It should be measured before a dataset is trusted for training or evaluation.

- **High IAA** suggests that the labels are reliable and the rubric is interpreted consistently.
- **Low IAA** may indicate unclear instructions, inherent task ambiguity, noisy examples, overlapping labels, or insufficient reviewer calibration.

A model trained or evaluated on inconsistent labels receives conflicting signals, which limits the meaning of its measured performance. Accuracy assumes that the reference labels are trustworthy; when human judgment is involved, consistency and agreement may provide necessary context for interpreting that accuracy.

IAA provides a practical benchmark for expected model reliability, although it is not always an absolute mathematical ceiling. If humans disagree frequently, teams should improve the rubric, examples, and adjudication process before demanding higher model performance.

### Inter-Annotator Agreement Metrics

- **Raw agreement** — The percentage of examples on which reviewers agree. It is simple to interpret but does not account for chance agreement and can be misleading when one label dominates.
- **Cohen's kappa** — Measures agreement between two reviewers on categorical labels. It adjusts observed agreement using the agreement expected by chance.
- **Fleiss's kappa** — Extends chance-corrected categorical agreement to three or more reviewers.
- **Krippendorff's alpha** — Supports multiple reviewers, missing labels, and different measurement scales. It is flexible but more difficult to calculate and configure correctly.

Cohen's kappa is a practical default for two reviewers assigning categorical labels. The appropriate metric should still be selected according to the number of reviewers, label scale, missing data, and implementation requirements.

#### Cohen's Kappa Calculation

Cohen's kappa compares observed agreement with the agreement expected by chance from each reviewer's label-use pattern:

```text
κ = (observed agreement − expected agreement) / (1 − expected agreement)
```

For example, suppose two reviewers agree on 85 of 100 items:

- Observed agreement = `0.85`
- Expected chance agreement = `0.50`
- Kappa = `(0.85 − 0.50) / (1 − 0.50) = 0.70`

Under one commonly used interpretation scale, `0.70` represents **substantial agreement**. Such labels are rules of thumb and should be interpreted in the context of the task and its risks.

Kappa is more informative than raw agreement when chance agreement is high, but it can still be affected by label prevalence and reviewer bias. For Krippendorff's alpha, `1` represents perfect agreement, `0` represents chance-level agreement, and negative values indicate disagreement greater than expected by chance.

These metrics provide quantitative evidence for deciding whether labels are reliable enough to train and evaluate models. Agreement also acts as a quality gate and diagnostic tool for improving rubrics and reviewer calibration.

### Diagnosing Agreement Patterns

IAA should be analyzed by difficulty, reviewer, and time rather than treated as one overall number.

| Pattern | Likely explanation | Appropriate response |
|---|---|---|
| Low agreement on easy cases | The rubric is underspecified, so reviewers apply different implicit criteria. | Clarify definitions, instructions, and examples. |
| Low agreement only on hard cases | The examples may be genuinely ambiguous or allow multiple valid answers. | Document the ambiguity and use adjudication or multiple acceptable labels instead of forcing artificial consensus. |
| Agreement declines over time | Fatigue, training wear-off, or interpretation drift may be affecting reviewers. | Refresh training and run calibration sessions. |
| One reviewer scores consistently higher or lower | The reviewer may have a systematic calibration bias. | Review that annotator's examples and provide targeted calibration. |

These patterns support focused improvements to rubric design, reviewer training, and labeling quality control.

### Example: Postal-Address Resolution

A postal-service project used machine learning to resolve poor-quality addresses while COVID test kits were being mailed to households across the United States. The system initially achieved **84% accuracy**, which stakeholders considered inadequate.

Evaluation of roughly **120 human-labeled examples** found that postal workers agreed with one another only about **83% of the time**. The comparison showed that the model was already operating near observed human consistency and that the labeling standard itself needed attention.

The team shifted effort toward refining the rubric and improving multi-review. With clearer standards and stronger agreement, the solution reached approximately **97% accuracy**.

Human agreement provides an important baseline for interpreting AI performance, although it is not always an absolute mathematical ceiling. Low agreement may indicate that improving the rubric and review process will produce more value than continuing to tune the model alone.

### Kappa Vitality

**Kappa vitality**, or **k-vitality**, is a leave-one-reviewer-out diagnostic that measures how each annotator affects overall agreement.

The process is:

1. Compute kappa with all annotators included.
2. Remove one annotator.
3. Recompute kappa for the remaining annotators.
4. Calculate `k-vitality = kappa without the annotator − kappa with all annotators`.
5. Repeat for every annotator.

With this definition:

- **Positive k-vitality** means agreement increased after removal, so the annotator may be reducing consistency.
- **Negative k-vitality** means agreement decreased after removal, so the annotator may be contributing positively.
- **Near-zero k-vitality** means the annotator has little effect on overall agreement.

Plotting these values across reviewers makes unusual patterns easier to identify. Results can guide targeted calibration, additional training, contribution reweighting, or, after careful review, exclusion from the task.

K-vitality should not be used to blame annotators automatically. Disagreement may come from an unclear rubric, poor examples, or genuine ambiguity. Examine the rubric and disputed cases first, then use reviewer-level diagnostics to choose the appropriate intervention.

## Prompt and Evaluation Stability

**Prompt stability** measures whether repeated runs on the same input produce consistently correct behavior.

### Types of Stability

- **Exact consistency** — The output is identical on every run. This is uncommon when non-zero temperature or other stochastic sampling is used.
- **Quality consistency** — Wording or details may vary, but correctness and overall quality remain equivalent. This is often the most practical production target.
- **Failure consistency** — Failures occur in a similar, recognizable way. Consistent failures are easier to reproduce, diagnose, test, and fix than random ones.

### Stability Levels

| Level | Behavior |
|---|---|
| **High** | Facts, correctness, and quality remain consistent across runs. |
| **Medium** | Overall quality remains stable, but wording or minor details vary. |
| **Low** | The same prompt is sometimes correct and sometimes wrong. |

Production prompts should generally target high or medium stability according to the task. Low-stability prompts are not production-ready because incidents are difficult to reproduce, debug, and test.

Stability should also be checked across small meaning-preserving input variations, prompt or model versions, configuration changes, different annotators, and evaluation rounds.

## Labeling Guidelines and Continuous Refinement

Labeling guidelines translate a rubric into instructions that reviewers can apply consistently.

### What Guidelines Should Include

- **Task definition** — Explain what is being labeled and why.
- **Explicit rubric** — Define the inputs, criteria, labels, and rating scales.
- **Worked examples** — Provide representative examples, ideally about three for each rating level when practical.
- **Edge-case guidance** — Explain how to handle ambiguous, incomplete, or unusual inputs.
- **Calibration examples** — Give reviewers shared cases for training and alignment.
- **Decision trees** — Break multi-step judgments into consistent decisions.

### Common Guideline Failures

- **Vague scales** — Asking reviewers to rate quality from one to five without defining each score.
- **Missing edge cases** — Forcing reviewers to invent their own rules.
- **Mid-project changes** — Making earlier labels inconsistent with labels created under newer guidance.
- **No calibration** — Allowing reviewers to interpret the same criteria differently.
- **Single-reviewer dependence** — Hiding disagreement, bias, and annotator drift.

### Treat Questions as Gaps

A useful rule is: **if a labeler asks a clarifying question, the guidelines have a gap**. Record the question, update the relevant rule or example, communicate the change, and relabel affected examples or classes when necessary.

Well-maintained guidelines improve inter-annotator agreement and keep gold datasets reliable as tasks and production inputs evolve.

## Importance Across the AI Lifecycle

Gold datasets and human evaluation support the entire AI lifecycle, not only prompt evaluation. They:

- Define what successful behavior looks like
- Anchor automated metrics in human judgment
- Provide a realistic benchmark based on human consistency
- Support training, comparison, deployment decisions, and production monitoring

Without carefully constructed gold standards, clear rubrics, and measured inter-annotator agreement, models are trained and evaluated on unreliable foundations. This can produce poor real-world performance, misleading claims, and expensive failures.

Investment in gold data, human labeling, agreement measurement, and guideline design is a core requirement for trustworthy, high-impact AI systems across domains.
