# 4.4 Task-Specific Evaluation for GenAI Workflows

[← 4.3 LLM Workflow Lifecycle](<4.3 LLM Workflow Lifecycle.md>) · [↑ Chapter Overview](<4. Prompt Optimization and Evaluation.md>) · [Next Topic: 4.5 Gold Datasets and Human Evaluation →](<4.5 Gold Datasets and Human Evaluation.md>)

Evaluation should begin with a clear, task-specific definition of success. Starting with prompts and judging a few outputs informally makes improvement subjective and hides regressions.

## Evaluation-Driven Development

Evaluation-driven development inverts the usual workflow by defining success before writing or optimizing a prompt. Begin with a **rubric**: explicit task-specific criteria describing a good output and how each quality will be measured.

The evaluation-first process is:

1. Define task-specific success criteria.
2. Build a rubric and a goal or evaluation dataset containing realistic inputs and desired outputs or properties.
3. Establish a baseline on a held-out evaluation set.
4. Change the prompt, retrieval strategy, model, or broader system design.
5. Measure every change against the same criteria and dataset.

This mirrors test-driven development, where tests are written before implementation and detect regressions automatically. Fixed evaluations replace statements such as *“I think this is better”* with evidence such as *“the held-out score increased from `0.7` to `0.8`.”*

The cost is front-loaded because teams must define rubrics and assemble evaluation data early. For systems expected to last beyond a short experiment, this investment makes later iterations faster to evaluate, easier to compare, safer to deploy, and more maintainable.

## Why Ad Hoc Iteration Fails

A common weak workflow is to write a prompt, inspect one output, tweak the wording, and repeat until the result *looks good*. This creates several problems:

- **Subjective improvement** — There is no measurement showing whether the change improves performance across many examples.
- **Overfitting to spot checks** — A prompt may improve the few examples being inspected while becoming worse on other inputs.
- **Hidden regressions** — Failures may remain invisible until production, where they are more expensive to diagnose and fix.
- **No objective comparison** — Without a fixed rubric and dataset, prompt, model, and configuration versions cannot be compared fairly.
- **Demo-to-production gap** — A workflow can appear strong in demonstrations but behave unpredictably during real use.

Production-ready GenAI systems require systematic evaluation instead of intuition and occasional spot-checking.

## Evaluation Ecosystem

Robust evaluation combines complementary methods because each one reveals different strengths and failures.

### Human Evaluation

Human review is the gold standard for subjective qualities such as nuance, tone, and overall usefulness. It captures details that automated metrics may miss, but it is slow, costly, and harder to scale consistently.

### Automated Metrics

Automated metrics provide scalable and reproducible scoring:

- **Reference-based metrics**, such as BLEU, ROUGE, and BERTScore, compare generated output with one or more reference answers.
- **Reference-free metrics**, such as perplexity or coherence scoring, assess properties of an output without requiring a gold reference.
- **LLM as a judge** uses a model and a defined rubric to score outputs, combining human-like judgment with automation. Its judgments must also be validated for consistency and bias.

### Benchmark Datasets

Benchmarks provide standardized comparisons across models. They help with broad capability assessment and model selection, but may not represent the inputs, criteria, or risks of a specific application.

### Adversarial Testing

Adversarial evaluation deliberately probes failure modes through:

- Red teaming
- Jailbreaking attempts
- Input perturbations
- Robustness and edge-case testing

These tests reveal policy circumvention, brittleness, and failures that normal evaluation data may not expose.

Production systems should combine human review for depth, automated metrics for scale, benchmarks for external comparison, and adversarial testing for resilience. Depending on only one approach leaves blind spots that may become real-world failures.

## Task-Specific Workflows

Three NLP workflows recur across many teams. Each has a different goal and characteristic failure mode, so each requires a tailored rubric.

### Question Answering

Question answering, especially grounded Q&A, is vulnerable to **hallucination**: plausible claims that are false or unsupported by the supplied source.

A Q&A evaluation rubric should cover:

- **Faithfulness and grounding** — Every claim should be traceable to the source, with no unsupported information.
- **Factual correctness** — Named entities, numbers, dates, and other facts should match the source.
- **Citation coverage** — Claims should cite or link to the correct supporting passages.
- **Answer completeness** — The response should address every relevant part of the question.
- **Scope discipline** — The answer should not go beyond the user's request or the evidence available in the source.

Typical failure modes include:

- Plausible hallucinations
- Partial answers to multi-part questions
- Correct facts attributed to the wrong passage
- Overreach beyond what the source supports
- Unjustified refusal when the source contains enough information to answer

A robust Q&A evaluation stack should include separate measures of faithfulness, answer correctness, and scope discipline because no single metric captures all these qualities.

### Summarization

Summarization is open-ended because one source can have several valid summaries depending on its purpose, audience, and required level of detail.

A summarization rubric should cover:

- **Coverage** — Are all key points from the source represented?
- **Coherence** — Does the summary read as a unified whole rather than disconnected fragments?
- **Omission risk** — Has any critical information been left out?
- **Audience appropriateness** — Does the detail and language suit the intended readers?
- **Compression** — Is the source meaningfully condensed without unnecessary verbosity?
- **Faithfulness** — Does the summary avoid claims not supported by the source?

Different summary types require different criteria:

- **Executive brief** — Prioritizes the bottom line, often in two or three sentences.
- **Detailed summary** — May include decisions, actions, and open items.
- **Stakeholder-specific summary** — Includes only information relevant to a particular group.

The audience and purpose must be defined before evaluation. The rubric should encode those requirements instead of assuming that one summary format is suitable for every use case.

### Classification

Classification assigns labels such as topic, sentiment, or urgency. It benefits from traditional machine-learning metrics but also requires checks for generative variability.

#### Core Metrics

- **Accuracy** — The overall proportion of correct predictions. It can be misleading when classes are imbalanced.
- **Precision** — Of the items predicted as a class, how many actually belong to that class?
- **Recall** — Of all items that truly belong to a class, how many did the model identify?
- **F1 score** — Balances precision and recall. Per-class or macro F1 is especially useful when class distributions are skewed.
- **Confusion matrix** — Shows which labels are commonly mistaken for one another.

#### LLM-Specific Checks

- **Consistency** — The same input should receive the same label across repeated runs. Use low randomness and deterministic decoding where supported.
- **Boundary-case handling** — Test genuinely ambiguous examples near the boundary between labels.
- **Calibration** — Check whether the model's stated confidence matches its actual correctness rate.

#### Common Pitfalls

- **Class imbalance** — Always predicting the majority class may produce high accuracy while failing minority classes.
- **Hidden bias** — The model may default disproportionately to the most common label.
- **Ambiguous labels** — Unclear label definitions or rubrics can create high disagreement.
- **Forced single labels** — Some inputs belong to multiple categories even when the schema allows only one.
- **Distribution drift** — Production inputs and class frequencies may change over time.

Never report accuracy alone. Combine it with precision, recall, F1, a confusion matrix, consistency checks, and other metrics relevant to the task.

### Separate Evaluation Harnesses

A single evaluation harness should not be reused blindly across these tasks. Each rubric must reflect the workflow's definition of success and its likely failures.

### Code Generation

Code generation is **semi-verifiable**. Generated code can be executed and tested, but passing tests does not prove complete correctness, maintainability, or safety.

A code-generation rubric should cover:

- **Functional correctness** — Does the code run and produce the expected outputs? Measure this with visible and hidden unit tests, including edge cases.
- **Specification adherence** — Does it follow the required signatures, types, interfaces, and contracts?
- **Code quality** — Is it readable, idiomatic, maintainable, and free of unnecessary or dead code?
- **Security** — Does it avoid injection vulnerabilities, unsafe input/output handling, secret leakage, remote-code-execution paths, and unauthorized shell operations?

#### Evaluation Techniques

Three complementary techniques are commonly used for code-generation evaluation.

##### Pass@k

**Pass@k** measures the probability that at least one of `k` sampled completions passes all tests:

- **Pass@1** measures first-try quality and is the stricter measure for single-shot use.
- **Pass@10** measures whether at least one of ten candidates succeeds, which is useful when a system can generate and select among multiple solutions.

##### Standard Benchmarks

Common code-generation benchmarks include:

- **HumanEval** — 164 hand-written Python programming problems with tests.
- **MBPP** — Mostly basic Python programming problems.
- **SWE-bench** — Real GitHub issues evaluated by whether generated repository changes resolve the issue and pass relevant tests.

Benchmarks support standardized model comparison but may not represent a specific repository, framework, or engineering standard. Application-specific workflows should therefore maintain custom test sets based on their own codebase and likely failures.

##### Execution-Based Evaluation

Run generated code against a real test harness and use pass/fail results as the primary correctness signal. Execution provides clearer evidence than visual inspection or textual similarity.

Passing the available tests still does not prove complete correctness or safety. Execution results should be combined with edge-case coverage, specification checks, code review, and security analysis.

Typical failure modes include:

- **Plausible but incorrect behavior** — Code may compile or look correct while containing logic errors, off-by-one mistakes, or failures on untested edge cases.
- **Hallucinated APIs** — The model may import libraries or call methods that do not exist. These errors often appear only during installation, compilation, or execution.
- **Version drift** — Generated code may target an older API version. It might fail immediately or continue running with incorrect behavior under the current version.
- **Unsafe patterns** — Remote-code-execution constructs, unauthorized shell operations, permission escalation, or unsafe input handling can create serious risks outside a controlled environment.

#### Mitigation

Always execute generated code in an appropriate controlled environment and test normal, boundary, and failure cases. Do not rely on visual inspection alone.

The code should also contain enough useful documentation for another developer to understand its important behavior and decisions. If the code cannot be explained clearly, slow down and request a clearer explanation or targeted comments before deployment. Model-generated explanations can support human review, but they do not replace execution, tests, or security analysis.

## Verifiable vs. Open-Ended Tasks

Automated evaluation can be organized around whether a task is verifiable, open-ended, or a mixture of both.

### Verifiable Tasks

Verifiable tasks are **convergent**: they have one correct answer or a small set of clearly correct outputs. They support objective checks such as:

- Accuracy and standard benchmark scores
- Exact match
- Regular-expression or assertion-based validation
- Programmatic test execution

Code and mathematics are common examples because their outputs can often be tested directly.

### Open-Ended Tasks

Open-ended tasks are **divergent**: several different outputs may be acceptable, and quality requires judgment. Evaluation may include:

- **Reference-based assessment** — Compare output with goal samples using lexical or semantic similarity.
- **Reference-free assessment** — Judge intrinsic qualities with a rubric, human review, or an LLM as a judge.

These methods assess qualities such as clarity, style, usefulness, coverage, and coherence.

### Hybrid Tasks

Most real-world workflows combine objective and subjective requirements. A Q&A system, for example, must provide factually correct information while also explaining it clearly.

A suitable evaluation strategy combines verifiable checks for correctness with judgment-based assessment of explanation quality, style, and usefulness.

## Metric Taxonomy

Metric categories provide a checklist for designing a balanced evaluation plan:

- **Accuracy metrics** — Measure how closely the output matches the expected answer and whether it is factually or logically correct.
- **Fluency metrics** — Assess whether the text is natural, readable, grammatically correct, and well formed.
- **Relevance and consistency metrics** — Check whether the output addresses the user's request and remains grounded in the correct context or source without drifting into unrelated content.
- **Safety and bias metrics** — Evaluate harmful or toxic content and whether different groups are treated fairly.

No single metric captures every aspect of quality. For example, an output may receive a high BLEU score because it overlaps strongly with a reference while still containing unacceptable toxicity.

A production evaluation plan should include at least one metric from every category relevant to the task and its risks. This provides a more complete view of quality and reduces blind spots created by optimizing a single score.

## Lexical vs. Semantic Metrics

### Lexical Metrics

Lexical metrics compare surface-level word or phrase overlap between generated output and reference text.

- **BLEU** measures n-gram overlap and applies a brevity penalty. It was originally designed for machine translation and favors exact wording, so it can undervalue valid paraphrases.
- **ROUGE** is primarily recall-focused and measures how much reference content appears in the candidate. Common variants include **ROUGE-1** for unigrams, **ROUGE-2** for bigrams, and **ROUGE-L** for the longest common subsequence. It is commonly used for summarization.
- **Exact match** returns `1` when an output exactly equals the reference and `0` otherwise. It works well for Q&A with fixed answers and structured prediction but is usually too strict for open-ended text.

For example, *“The cat sat on the mat”* and *“The feline rested on the rug”* express similar meaning but share few n-grams, so a lexical metric may assign a very low score.

Lexical metrics reward text that looks like the reference rather than text that necessarily means the same thing. For open-ended generation, use them mainly as sanity-check baselines alongside semantic and task-specific evaluation.

### Semantic Metrics

Semantic metrics compare meaning rather than relying only on exact word overlap.

#### BERTScore

**BERTScore** uses contextual embeddings from a model such as BERT to compare candidate and reference tokens in embedding space. It is more tolerant of paraphrasing than lexical metrics.

For example, *“The feline rested on the rug”* and *“The cat sat on the mat”* can receive a high semantic-similarity score even though they share few exact words. BERTScore quality depends on the selected embedding model and its coverage of the language and domain being evaluated.

#### COMET

**COMET** is a learned evaluation metric designed mainly for machine translation. Depending on the COMET model, it can use the source text, the generated translation, and a reference translation to predict quality. Because it is trained using human judgment data, it often aligns more closely with human assessments than pure overlap metrics.

#### Practical Use

For open-ended generation, semantic metrics usually provide a stronger reference-based signal than lexical overlap alone. Pair them with human review or an **LLM as a judge** for qualities that embedding similarity may not capture fully, such as complex instruction adherence, style, usefulness, or safety.

This combination provides a broader evaluation than either lexical or semantic similarity alone.

### Lexical and Semantic Comparison Examples

| Scenario | Reference | Model output | Expected interpretation |
|---|---|---|---|
| Rephrasing | “Revenue grew 12% year-on-year.” | “Year-on-year revenue increased by 12%.” | Lexical metrics may score lower because of reordered or changed wording, while semantic metrics should score highly because the meaning is preserved. |
| Added qualifier | “Retry on timeout.” | “Must always retry on timeout.” | Lexical overlap is high, but *always* introduces a stronger requirement. A semantic metric may lower the score, although some embedding metrics can still miss the importance of this qualifier. |
| Exact match | “Paris is the capital of France.” | “Paris is the capital of France.” | Both lexical and semantic metrics should score highly. |

Score differences can help diagnose behavior:

- **Low lexical and high semantic scores** may indicate a valid paraphrase.
- **High lexical and lower semantic scores** may indicate over-specification or a shift in meaning.
- **High scores from both** indicate strong similarity, but do not replace factual, safety, or task-specific checks.

Using both metric types makes paraphrasing and unintended meaning changes easier to identify.

## Metric Alignment

Each task requires metrics that reflect its real definition of success.

| Task | Useful metrics | Misleading when used alone |
|---|---|---|
| **Question answering** | Answer correctness, groundedness, citation accuracy, and completeness | BLEU or ROUGE, because different wording can be equally correct and high overlap does not prove factual accuracy |
| **Summarization** | Coverage, conciseness or compression, faithfulness, and factual accuracy | Output length, because a short summary may omit essential information |
| **Classification** | Precision, recall, F1, confusion matrices, and consistency | Accuracy, because majority-class predictions can hide failures on minority classes |
| **Code generation** | Syntax checks, functional tests, specification adherence, and security checks | Syntax or textual similarity alone, because similar-looking code can behave differently in logic and performance |

Poorly aligned metrics can be gamed. A team may increase the measured score without improving actual quality and may even make the user experience or safety worse.

Select a balanced set of task-specific metrics that represents user value, expected failure modes, and safety requirements. Optimization will move toward whatever is measured, so the metrics must reward the behavior the system genuinely needs.
